## What was built to make this wave possible

### `tools/wave_worklist.mjs` — a work list derived from the DECISION queue

`build_generation_queue.mjs` decides "already done" from `qc.json.verdict`. Under
V4 that is wrong in both directions: a craft the owner REJECTED but QC passed is
treated as finished (its retry never queues, V4 §7), and a craft the owner
APPROVED but QC failed is queued for a credit-spending regeneration (V4 §6
forbids regenerating an approved image). The new tool reads
`data-store/generation-queue.json` states B and C — built from the merged ledger,
so both decision sources are already reconciled — and clusters on the proven-safe
`part|field|option|label` key plus the blueprint.

Result: **367 catalog rows collapse to 219 distinct photographs**, of which 196
are generatable and 22 are withheld (below). `prep_batch.mjs` gained
`--worklist=` and now skips its QC-verdict "already done" test when fed a
decision-queue list.

## Four prompt-builder defects found and fixed BEFORE spending on them

1. **`No.1` read as the word "no".** `isAbsence()` matched `^no\b`, and `\b` sits
   between "no" and ".". The whole `No.1` lapel-buttonhole family (**9 catalog
   rows, 3 distinct crafts**) was being described to the image model as *"the
   deliberate ABSENCE of the lapel buttonhole style"* — it would have rendered a
   blank lapel and sold it as a two-colour handmade buttonhole. Fixed in
   `spec.mjs` (`isAbsence`), in the `forbidden[]` builder, and in the separate
   framing predicate in `prompt.mjs`. **Verified in the output**:
   `lbh-no1-tc-arc` now shows a real three-colour arc buttonhole.

2. **A per-side count read as a whole-garment total.** `lbp-both`
   ("One buttonhole on each lapel") produced `COUNT LOCK — EXACTLY 1 buttonhole`
   and `forbidden: 2 where the specification says 1` — the prompt forbade the
   correct garment and demanded the neighbouring single-sided option. `countLock`
   and `countNegatives` now detect per-side phrasing and state both figures
   ("1 on each side, 2 in total"). **Verified in the output**: one buttonhole on
   each lapel, both sides in frame.

3. **The owner's styling ruling was not in the builder.** `jacket-lapel` styling
   said "NO necktie and nothing at the throat" (documented reasoning: a tie hides
   the lapel foot). The owner rejected that: *"give the model a tie i never want a
   unbuttoned shirt with no under shirt."* The owner's decision is authoritative;
   `camera.mjs` now requires shirt buttoned to the collar plus a neat slim tie,
   constrained so the tie stays clear of the lapel edges and the closure point.

4. **Rejection reasons emitted twice** (see `fold_queue_rejections.mjs` above).

## The generation path, for the next run

The platform API (`tools/run_generation.mjs --probe`) returns
`403 not_enough_credits` on every reference-field candidate: **the
cloud.higgsfield.ai API account bills separately from the Plus/MCP account**
(603.88 credits there, zero on the API). Until API credits are bought, generation
runs through the MCP connector, which means each prompt is relayed by hand —
roughly 6 KB per craft.

What makes that workable:

- **`media_import_url` instead of signed uploads.** Every blueprint is already
  served publicly at `https://customsuits.net/images/...` (all 40 verified 200

- **`data-store/higgsfield-media-map.json`** — a durable url → media-uuid map, so

  costs a re-upload. `tools/attach_media_ids.mjs --apply` re-attaches blueprints

  is spent at generation; the artifact is durable only on disk. Job ids are
  written to `public/images/reports/wave-02-jobs.json` at submission time, before
  the wait, so a crash between the two loses nothing. Attempt numbers come from
  the filesystem, never from `qc.json`, so no paid candidate can be overwritten.

## `pocket-depth` → `KPOKS` — a mapping no matcher could make

KPOKS/B draws a trouser front with the pocket BAG outlined deeper than the
standard. But the two systems express depth differently:

```
ours    : Shallow (20 cm)   Standard (23 cm)   Deep (26 cm)
supplier: Reduce 3cm        Standard           Add 3cm
```

Our catalog states Standard = 23 cm and the supplier states depth as a DELTA
from standard, so 20 cm is "Reduce 3cm" and 26 cm is "Add 3cm". There is exactly
one consistent assignment. It is forced — but it is arithmetic, and no amount of
string matching will ever see it.

So `apply_field_mapping.mjs` gained an **explicit alias** escape hatch: a
documented per-option mapping, applied before matching, that claims its plate so
nothing else can take it. Used only where the correspondence is provable and not
textual. **9 rows.**

## Session 19g — the swatch-exclusion rule has a bug, and fixing it is NOT a small change

The 4 identities the wave worklist withholds for a shared blueprint are all
`lining-color`: **Matching to Fabric / Black / Cream / Dark Charcoal**, and all
four point at one drawing, `0711__Match_fabric.webp`. Of course they do — a line
drawing cannot express a colour.

They should never have been in scope. The mission excludes fabric swatches and
thread colours outright, and the sibling fields agree:

| field | states |
|---|---|
| `sleeve-lining-color` | X 15 — fully excluded |
| `vest-lining-color` | X 12 — fully excluded |
| `lining-color` | **X 15, C 12** ← inconsistent |

Inside `lining-color`, `bl-navy`, `bl-burgundy`, `bl-gold-paisley`, `bl-pattern`
and `bl-custom` are excluded as *"fabric"*, while `bl-matching`, `bl-black`,
`bl-cream` and `bl-charcoal` are not — the same field, the same kind of option.
`sl-black` is excluded while `bl-black` is not.

**The cause.** `classifyExcluded` treats a text as geometry (and so keeps it) when
it matches `/position|placement|coverage|shape|craft|where|height|width|length|depth/`,
and it runs that test over the option's **description**. The four survivors are
kept because their marketing prose contains the English word **"where"**:

> "…black-tie jackets, **where** it creates a seamlessly dark interior…"

`where` is a conjunction, not a placement noun. `bl-black` also trips on `depth`
("adds depth"). The comment above the call says the test is *"Considered across
fieldId + fieldLabel + the option label itself"* — the description was added
later and is what broke it.

**Why I did not fix it.** Three variants were measured against all 2,862 options:

| change | options reclassified |
|---|---|
| placement from field+labels, fabric test on full text | **67** — wrongly excludes cuff styles, chest pockets, lapel styles, sleeve vents, pleats, whose prose mentions fabric in passing |
| both tests from field+labels | **68** — and many move the *other* way: `canvas`, `lapel-style`, `button-config`, `elbow-patch` would leave exclusion and enter generation |
| drop the bare `where` token | does not fix `bl-black`, which also trips on `depth` |

Every variant reclassifies ~68 crafts, some into paid generation and some out of
it. That is a scope decision with a cost attached, not a bug fix, and it is not
mine to make silently.

**Nothing is at risk meanwhile.** All 4 are already withheld from the wave for the
shared-blueprint reason, so no wrong image can be generated from them. They sit
in state C, counted honestly, changing nothing.

**For the owner:** the 12 `lining-color` rows are colour swatches and by the
mission's own rule should be excluded like every other lining-colour field. That
is a 12-row change. Repairing the underlying classifier is a separate, larger
decision affecting ~68 crafts in both directions.

Evidence: `public/images/reports/id-label-shape-conflicts.json` and the measured
variants above.

## Session 19h — measurement fidelity, and a checker that lied

V4 requires **real measurements**, not "wide" or "narrow": *"Peak lapel 8 cm,
9 cm, 10 cm … Not just 'wide.' Actual measurements."* A prompt for "Peak 101°"
that never says 101° leaves the model to guess, and every peak angle we sell
collapses onto one generic lapel — which is exactly the shared-plate defect this
project has already paid for once.

New check, `measurement-dropped`: if the option **label** states a dimension, the
prompt must state that same dimension.

Result across the staged batch: **38 prompts carry a measurement in their label,
and 0 are missing it.** Confirmed — this axis is clean.

### The checker reported 38 of 38 broken, and was wrong

Worth recording because it is the second time this session.

The first version built one regex per measurement:
`` `\b${n}(\.0)?\s*${unit}` ``. Written inside a shell-quoted `node -e`, the
backslashes did not survive: the regex that actually ran was
`\b13(.0)?s*cm` — `\s` had become a literal `s`, `\.` a wildcard, and `\b` a
**backspace character**. It matched nothing, so every prompt looked broken.

Earlier in this run the same class of bug produced a literal `0x08` inside
`/(\d)\s*(cm|mm)^H/g`, which also silently matched nothing.

Both were found the same way — by printing the regex that actually ran instead of
the one that was intended. The rewrite avoids the whole class: every measurement
is canonicalised to `"<number><unit>"` (no spaces, no trailing zeros) and
compared by **set membership**. There is nothing left to escape.

`audit_prompts.mjs` now runs eight checks: absence-vs-label, per-side-count,
phantom-references, duplicate-correction, missing-correction,
label-vs-description, leaked-placeholder, measurement-dropped.

### Final integrity pass on what would actually be generated

## Session 19i — the prompts were being thrown away

`prep_batch.mjs` called `build_prompt.mjs --json` and never `--write`. The prompt
therefore existed only inside that process and inside `batch-payload.json`, which
the very next batch overwrites. **That is the root cause of the 29 candidates
sitting in `/admin/image-review` with no recoverable prompt** — V4 §11.7 requires
the review screen to show the prompt an image was made from, and it had been
discarded the moment the batch moved on.

Adding `--write` fixes a second thing too. `build_prompt` applies the spec-only
language transform — `BLUEPRINT LOCK` → `SPECIFICATION LOCK`, *"reproduce exactly
as drawn"* → *"as specified"* — **inside the `--write` branch**, which runs before
`--json` and mutates the same object. Calling with `--json` alone returns the
untransformed text, so the payload and any saved file would have disagreed for
exactly the crafts where the wording matters most: the ones with no drawing.

Both worklists were then rebuilt so every identity carries a persisted
`prompt.json`, not just a transient one.

### The 181 deploy-blocked crafts are built too

They cannot be generated — Higgsfield imports the drawing by URL and theirs 404 —
but their specs and prompts are worth building **now** so a defect is found before
the deploy rather than after it. `wave-worklist-pending-deploy.json` holds them
(156 sport-coat, 12 shirt, 8 suit-2pc, 5 suit-3pc); `--no-verify-urls` builds them
without pretending they are generation-ready, and the payload is kept separately
as `batch-payload-pending-deploy.json` so it can never be mistaken for the live
batch.

"accurate" but shot at six different distances passes QC and still misleads the
customer.

→ `public/images/reports/measurement-families.json`

**Recommended, not done:** a sibling-set QC pass that loads a whole family at once
and checks constant framing — garment scale, crop, camera distance — before any
member of it is published. It is the one quality gate this pipeline does not have,
and 444 rows depend on it.

### The sibling gate found the defect immediately — MATCHED FRAMING is not holding

`tools/sibling_framing_sets.mjs` assembles the comparison sets per-image QC cannot
see. Ten sets are already **complete** (every member shot) from earlier waves, so
the gate could be tested on real output at once.

First set opened — `suit-2pc/lower-pocket`, "Slanted Flap", six members differing
by nothing but flap depth:

| member | camera | flap share of frame | cloth | trouser |
|---|---|---|---|---|
| **4.0 cm** | furthest — hand, shirt cuff and front button all in frame | ~30% | plain navy birdseye | navy |
| **5.0 cm** | mid | ~55% | soft navy flannel | **grey** |
| **6.5 cm** | closest — no hand, no cuff | ~55% | navy **twill / serge** | navy |

Three members, three camera distances, three different cloths, and one of them in
grey trousers. **The 5.0 cm flap occupies as much of its frame as the 6.5 cm flap
does of its own.** A customer comparing 4.0 against 5.0 would read the difference
as roughly double; it is 25%.

Every one of these images is individually good — sharp, realistic, faithful to its
own drawing — and every one would pass `garment-image-qc`, because QC grades one
image against one illustration and never sees the set. That is precisely the hole:

> V4: *"The customer should be able to compare any two craft options side-by-side
> and immediately understand the construction differences."*

That is a test **on the set**, and nothing was applying it. `build_prompt` emits a
well-written MATCHED FRAMING clause for exactly these families — it even separates
the two failure modes, exaggerating the feature versus moving the camera — but a
clause in a prompt is a request, not a guarantee, and the evidence says the model
is not honouring it.

**Scope: 88 families, 444 generatable rows — about a quarter of everything in
scope.** Ten sets are complete today and can be reviewed immediately;
`public/images/reports/sibling-framing-sets.json` lists them with every member's
latest candidate path.

This is not fixable by editing the prompt harder. The options are structural:

1. **Generate a family in one pass** — one image containing the whole range, or a
   fixed anchor image reused as a reference for every member, so the camera cannot
   drift between siblings.
2. **Composite after the fact** — shoot each member, then normalise scale and crop
   programmatically against a common landmark before publishing.
3. **Accept per-member variation and never show them side by side** — which
   contradicts the mission.

Not decided here; it changes how ~444 rows get produced and is the owner's call.
What is decided: these sets must not be published as a comparison set in their
current state.

## Session 20b — wave-03 complete, and the owner's own photographs were never being sent

**39 generated by a fanned-out workflow (8 groups, 0 failures), plus the 1 probe
and the 1 hand-run = 40. All 40 recorded in `wave-03-jobs.json`.** The subagents
verified prompt fidelity byte-for-byte against the ledger before submitting.

The agents raised three flags. One does not survive checking; two do.

### FLAG 1 — "the whole wave rendered at the cheapest tier". True, but not a defect.

Every job came back with `params.resolution → 1k`, `params.quality → low`, both
"default for model", against prompts asking for *"Phase One IQ4 medium-format,
150MP detail"*. Measured output: **880×1168 = 1.03 MP.**

`gpt_image_2` does offer more, at a price:

| resolution / quality | credits | vs default |
|---|---|---|
| 1k / low *(used)* | **0.5** | 1× |
| 1k / medium | 2 | 4× |
| 2k / medium | 3 | 6× |
| 2k / high | 7 | 14× |
| 4k / high | 12 | 24× |

But sampling what is **already published**: 25 of 40 catalog images are
**880×1168** — identical to this wave. The new images match the established
library rather than under-delivering it. Raising the tier is a live option
(371 identities at 2k/medium ≈ 1,113 credits against a ~573 balance), but it is a
budget decision, not a repair.

### FLAG 2 — 25 prompts claim the owner's photographs are attached. None were.

This is the real one, and it is the most expensive gap the pipeline has had.

When an owner rejects an image they can upload photographs of what the option
should actually look like. `build_prompt` then writes, verbatim:

> **OWNER REFERENCE PHOTOGRAPHS** — 4 real photograph(s) of THIS exact craft
> option, supplied by the owner and **attached** alongside the drawing…
> Those photographs **OUTRANK the supplier line drawing** wherever the two
> disagree.

Measured: **25 of 190 staged prompts say that. 41 photographs exist on disk. All
41 return 200 from the origin. Not one had ever been attached** — the payload
never carried them, so the submitter had nothing to send. The model was told to
defer to evidence it could not see, on precisely the crafts the owner had already
rejected once.

Two went through wave-03 that way. `suit-2pc/ext-straight`'s recorded rejection
reason is **"Unrealistic / AI look"** — exactly what a real photograph fixes.

**Fixed**: `prep_batch` now emits `ownerReferenceUrls` (non-withheld only,
existence-checked, as importable public URLs) so a submitter can attach them.

**Proven, not assumed.** `ext-straight` regenerated with all four photographs
attached:

- **attempt 2** (illustration only): a tight macro of an outsized pointed tab
  lying across the band — schematic, the tab appliquéd rather than integral,
  filling most of the frame. Reads as a diagram of a tab.
- **attempt 3** (illustration + 4 photographs): a real trouser front — correct
  waistband proportion, belt loops, pleat, pocket, and a correctly **scaled**
  pointed tab carrying one button and one hook-bar.

One honest trade-off: attempt 3 is less of a macro than the prompt's
"filling 40–60% of the frame" asks for. It bought realism with framing. Given the
rejection reason was realism, that is the right trade — but the prompt and the
photographs now pull in different directions, and the prompt should probably
relax the macro demand when references are attached.

**24 crafts still carry the claim without ever having had the photographs.** They
should be regenerated with references attached before any of them is reviewed —
about 12 credits at the current tier.

### FLAG 3 — a prompt that contradicts itself

`sport-coat/lapel-shawl-0a` describes *"Narrow shawl lapel with a smaller sweep
radius … the modern tuxedo shawl"* while its owner correction — which the prompt
instructs the model to obey **over** the BLUEPRINT LOCK — specifies *"Classic
Shawl Lapel, Lapel Width: 10.5 cm"*. Narrow-modern and classic-10.5 cm are
different lapels. The prompt asks for both and ranks them against each other, so
the geometry is not deterministic and QC verdicts on this option will be unstable
across attempts however many times it is retried. A defect in the stored prompt,
not in the run; retrying cannot fix it.
